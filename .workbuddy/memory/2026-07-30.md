## 修复：Zhai.PictureView 打开 AI / PDF 失败

### 现象
用户实测 AI、PDF 打不开（PSD 用 Magick 原生不受影响）。

### 根因（实测坐实，非推测）
- Magick.NET 12.3.0（Q16-AnyCPU）对 Ghostscript 的调用机制：
  - 设环境变量 `MAGICK_GHOSTSCRIPT_PATH` → 会让 Magick 尝试**执行外部进程 `gswin64c.exe`**（视为 gs 可执行文件路径），而非加载 dll；该 exe 不在 PATH 时直接报错 `FailedToExecuteCommand "gswin64c.exe" ... 系统找不到指定的文件`，且不加载任何 GS 模块。
  - 正确做法：`MagickNET.SetGhostscriptDirectory(含 gsdll 的目录)` → Magick **直接加载目录里的 gsdll64.dll 库**，无需 gswin64c.exe、无需系统 Ghostscript。
- 之前两轮“验证成功”都是假的：沙箱本机装了系统 Ghostscript，Magick 自动从注册表回退到系统 `gsdll64.dll`，所以一直没验证到打包的 dll。把系统 GS 移开也无法安全做（Program Files 受限），最终用“分进程打印已加载模块路径”的隔离手法确认：只有 `SetGhostscriptDirectory` 模式真正加载了打包的 `gsdll64.dll` 并解码成功。

### 改动
- `src/App.xaml.cs`：`ConfigureGhostscript()` 去掉 `Environment.SetEnvironmentVariable("MAGICK_GHOSTSCRIPT_PATH", ...)`，改为 `MagickNET.SetGhostscriptDirectory(AppDomain.CurrentDomain.BaseDirectory)`（需 `using ImageMagick;`）。csproj 已把 `gsdll64.dll` 拷贝到输出根目录，故该目录即 BaseDirectory。

### 验证
- `dotnet build -c Debug`：0 错误。
- 隔离测试（分进程打印加载模块）：`SetGhostscriptDirectory` 指向含打包 dll 的目录 → 加载 `...\gsdll64.dll` → PDF/AI 均 `417x208` 解码成功；环境变量/无效路径两种模式均失败。结论可靠。
- 重启程序（PID 27160，旧进程已结束）。

## 重要修正（本轮推翻上一版结论，才是真正根因）

上一版说“`SetGhostscriptDirectory` 直接加载 gsdll64.dll 即正确”是**错的**。沙箱里那次“成功”纯属假象——本机系统 Ghostscript 的 `gswin64c.exe` 在 PATH 里，被 Magick 的 delegate 机制捡漏调用了。

### 真正根因（本轮实测坐实）
- Magick.NET 读 PDF / AI / PS / EPS 时，走 ImageMagick 的 **delegate**，调用的是 **Ghostscript 命令行可执行文件 `gswin64c.exe`**，而不是去加载 `gsdll64.dll` 库。
- 只打包 `gsdll64.dll`（无论用 `SetGhostscriptDirectory` 还是环境变量）→ Magick 仍然去执行 `gswin64c.exe` → 找不到 → `FailedToExecuteCommand "gswin64c.exe" ... 系统找不到指定的文件` → PDF/AI 打不开。
- 早期判断“用户机器没装系统 GS”也对，但**修复方向错了**：光有 dll 不够，必须提供 `gswin64c.exe`。

### 真正可行的方案（已验证）
1. 打包**完整** Ghostscript 到 `src/Libs/Ghostscript/`：
   - `bin/gswin64c.exe`、`bin/gsdll64.dll`（从系统 `C:\Program Files\gs\gs10.01.2\bin\` 复制）
   - 同级 `lib/`、`Resource/`、`iccprofiles/`（gs 按 exe 位置自动推导资源目录，无需设 GS_LIB）
2. `App.xaml.cs` 启动期把 `Ghostscript\bin` 加入 `PATH`（让 Magick 的 `gswin64c.exe` 调用能定位），并保留 `MagickNET.SetGhostscriptDirectory`（无害）。
3. csproj 用 `<Content Include="Libs\Ghostscript\**">` 带目录结构拷到输出 `Ghostscript/`。
4. 启动时做一次自检：用 `MagickImage.Read(测试PDF)` 真解一页，失败就弹诊断窗 + 写 `gs_error.log`（含进程位数、gswin64c.exe 是否存在、异常类型）——告别盲猜。

### 验证（本轮，确凿）
- 直接调用 `gswin64c.exe`（PATH 指向 bin，不设 GS_LIB）→ 脱离系统 GS 独立栅格化 PDF 成功。
- App 启动自检不再生成 `gs_error.log`（Release 发布版与 Debug 版都通过）。
- 镜像 `GetDocumentBitmapSourceAsync` 真实路径（`PATH→gswin64c.exe` + `Density=150` + 文件方式读）→ PDF 417×208、AI 417×208 均解码成功。

### 另一个隐藏坑（AnyCPU 不拷原生库）
- `dotnet build` 的 AnyCPU 产物**不拷贝** Magick.NET 原生库 `Magick.Native-Q16-x64.dll` → exe 缺它，整个 Magick 起不来（PSD 也跟着挂）。
- 修复：csproj 固定 `<RuntimeIdentifier>win-x64</RuntimeIdentifier>`（或发布用 `dotnet publish -r win-x64`）。已固定，输出路径变为 `bin/.../win-x64/`，`.ps1` 路径已同步修正。

### .gitignore 坑
- 第 21 行 `[Bb]in/` 会忽略 `Ghostscript/bin/`，导致 `gswin64c.exe`/`gsdll64.dll` 不进仓库。已加例外：`!src/Libs/Ghostscript/bin/`、`!.../gswin64c.exe`、`!.../gsdll64.dll`。

### 用户“打不开”的主因（定位结论）
- 用户实际运行的是**旧发布目录** `Zhai.PictureView/v1.2.2.27/win-x64/Zhai.PictureView.exe`（2023 年旧版，只有 Magick.Native、没有 GS 包）→ PSD 等基础格式能开，AI/PDF 不行。
- 已用完整新包**覆盖**该发布目录（旧 exe 备份为 `Zhai.PictureView.exe.20260730.bak`）。用户直接运行此路径即可，无需再动源码。
- 源码仓库 `Zhai.PictureView_src` 已提交完整 GS 包，自包含。

## 续诊：透明丢失 + 横纹（SkiaSharp 解码路径）——本轮

### 用户新反馈
- 两个独立缺陷，都在"常见格式"解码路径（SkiaSharp）：
  1. 一张图**没有透明度**（带 alpha 的 PNG/WebP 显示为不透明）。
  2. 另一张图**看着有横线**（"横横断开"）。
- 用户明确问"有没有第三方库"。

### 链路定位（读代码确认）
- 常见格式（jpg/png/bmp/gif/ico/webp/wbmp/jfif）→ `GetWriteableBitmapAsync` 走 **SkiaSharp** `SKBitmap.Decode → ToWriteableBitmap()`（ImageDecoder.cs:264）。
- 其余格式 → `GetDocumentBitmapSourceAsync` 走 **Magick.NET**（前面已验证渲染正确、alpha 正确）。
- 主图 `ZDY:ImageView.ImageEffect = CurrentPictureEffect.Effect`，默认 `CurrentPictureEffect=null` → 默认无特效；特效 .ps 均为编译好的 ps_2_0 字节码，csproj 第 98–145 行已 `<Resource Include>` 嵌入 → 特效系统本身没坏。

### 结论 / 建议（待用户批准）
- "没有透明度"与"横纹"最可能在 **SkiaSharp 解码 / ToWriteableBitmap 的 alpha 与通道/stride 处理**；Magick.NET 作统一解码器可同时解决两者（alpha 保留、解码稳健）。
- 不引入新依赖：项目已引用 Magick.NET-Q16-AnyCPU 12.3.0。最小改动：把 `GetBitmapSourceAsync` 常见格式分支由 `GetWriteableBitmapAsync` 改为 `GetDefaultBitmapSource(fileInfo, autoOrient:true)`；或改 `GetWriteableBitmapAsync` 内部用 `new MagickImage(bytes) → ToBitmapSource()`。
- 横纹若来自某张具体图的编码，Magick 仍是最稳解码器。

### 验证环境限制
- 沙箱无界面，`ToWriteableBitmap()`/WPF 启动即崩，无法在此跑 SkiaSharp 的 WPF 转换复现；纯 Magick 解码（含 .ai 渲染、PNG 生成）可正常跑并产出文件。结论基于代码链路 + Magick 既有正确性。

## 修复落地：拖入卡死 + CDR 缩略图慢（2026-07-30 晚）

### 用户实测结论
- 多拖动几次到窗口 → 窗口直接卡死（拖入阻塞主因，比"慢"更致命）。
- CDR 加载太慢；AI/PDF 用户确认还好；SVG/PSD/PSB 本轮先搁置。

### 根因（代码级，已改）
- **拖入卡死**：连续拖入时 `OpenPictureAsync` 没有取消上一次未完成的 `Folder.LoadAsync`，多个加载并发，每个都在 UI 线程 `Dispatcher.Invoke(Add)` 逐文件冲刷 `CollectionChanged`；旧 Folder 还继续往自己里 Add（仍狂刷同一条 UI Dispatcher）→ 整条 UI 线程被淹没卡死。叠加 `LoadBorthers`/`CanAccess` 在 UI 线程同步做 `GetAccessControl`+`EnumerateDirectories`+`EnumerateFiles().Any()`。
- **CDR 缩略图慢**：`PictureThumbService` 用单线程串行 `AsyncTaskQueue`，每张 CDR 缩略图 = 一次 `cdr2xhtml.exe` 进程转换，几十张只能一张张排队；且 `OnPicturePropertyChangedCallback` 里 `if (image.IsLoaded) return;` 因虚拟列表容器回收后 `IsLoaded` 仍为 true，导致回收后新绑定的 CDR 永不生成缩略图（永远占位图）。

### 改动（5 文件，备份 bb62bab → 完成 24b1931）
- `Folder.cs`：新增 `AddRange`（批量 `Items.Add` + 单次 `Reset`）；`LoadAsync` 增 `CancellationToken`，后台枚举→按 ~300 一批 `BeginInvoke(AddRange)`（每批检查取消）；`LoadBorthers` 整体移入 `Task.Run`（含 `CanAccess`），仅最后事件回 UI；补 `using System.Collections.Specialized;`。
- `PictureWindowViewModel.cs`：新增 `_loadCts`；`OpenPictureAsync` 进入即 `Cancel+Dispose` 旧 CTS、立即解绑+`Cleanup` 旧 Folder，斩断并发叠加；`IsAccessed` 改 `await Task.Run`；token 传入 `LoadAsync`；`Cleanup` 里也取消 CTS。
- `MainWindow.xaml`/`.cs`：根 `FamilWindow` 加 `DragOver="PictureWindow_DragOver"`；新增 `PictureWindow_DragOver`（`GetDataPresent(FileDrop)`→`Effects=Copy;Handled=true`，否则 `None`）。
- `PictureThumbService.cs`：串行 `AsyncTaskQueue` 改为 `SemaphoreSlim(Max(2,ProcessorCount))` 有界并发 `QueueThumb`（多 CDR 并行转换）；移除 `image.IsLoaded` 早返回（依赖 `DrawThumb` 自身 `ThumbState!=Failed` 守卫）；删冗余 `using Zhai.Famil.Common.Threads;`、补 `using System.Threading;`。

### 验证
